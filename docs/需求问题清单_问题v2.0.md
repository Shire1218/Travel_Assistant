# 需求澄清问题清单（第 2 轮）

> 前置：本清单基于《需求澄清问题清单v1.0.md》的回答整理，聚焦数据模型、交互细节、技术选型三个层面。
> 带【建议】的问题可直接回复"同意"或提出修改。回答方式与上轮相同：按编号回答或直接在文件里批注。

## 〇、先确认 3 个要点

**P1 ⚠️ 登录与数据隔离的矛盾**：H36 要求部署到服务器供他人使用、A4 要求计划间数据隔离，但 A3 说第一版不实现登录——没有用户身份，多人数据就会混在一起无法隔离。建议第一版直接实现登录（Vben Admin 自带完整的登录/权限体系，边际成本很低）。

**P2 ⚠️ 优化算法的定位**：第一轮选了"先简单排序"，I40 又期望"真正的优化算法"。好消息：I41 数据量级为百级、单日景点通常 ≤10~12 个，第一版直接用精确算法（分支定界/动态规划）即可在毫秒级得到全局最优，成本可控，不需要遗传算法。即：第一版就能上"真优化"。

**P3 F27 行程结构的审核意见**（你让我再思考，结论如下）：
`计划 → 天（日期 + 当晚住宿酒店）→ 每天若干"交通 + 活动"序列`，另需补充三点：
- a) **候选池**：新录入的景点/活动先进池，再分配到某天（符合"先收集后排期"的习惯，也是半自动排程的前提）
- b) 每天**记录当晚住宿酒店**，才能支持中途换酒店
- c) **跨城交通段**作为特殊行程段，挂在出发日或到达日

## A. 用户与数据归属

1. 计划可见性：默认私有（仅创建者可见可编辑），对吗？同系统内是否需要"授权指定用户查看"？
2. 共享景点库：用户 A 录入的景点，用户 B 能否看到并加入自己的计划？【建议：全局共享，一人录入大家受益；"景点收藏"基于此库】
3. 景点被计划引用后的同步问题：景点库中信息更新（如门票涨价），已引用它的历史计划是否跟着变？【建议：计划保存引用+当时快照，库更新后提供"同步最新"按钮，避免历史计划被意外改动】
4. 景点去重：同一景点被不同用户各录一份怎么办？【建议：录入时按"名称相似+坐标相近"提示已存在可直接使用，不强制合并】

## B. 目的地与地图交互（重点）

5. "城市（大目的地）"的角色：仅作为计划属性和景点分组标签，还是作为严格的层级容器（城市→景点树）？【建议：轻量角色，用于分组展示/筛选/跨城段归属】
6. 景点所属城市如何确定：用户手选，还是按坐标逆地理编码自动判断+可改？【建议：自动+可改】
7. 地图选点（D22 重点功能）的交互形态，以下哪些都要：
   - a) 地图搜索框搜 POI（输"故宫"→结果列表→加入）
   - b) 地图上点击任意位置创建自定义地点（坐标自动取，名称手填）
   - c) 已有地点在地图上可拖动微调位置
8. 自定义地点（无 POI）字段：名称+坐标必填，地址/城市可选，对吗？
9. 地图上已入计划的景点如何呈现：【建议】按天着色的标记点+当天路线连线+游览序号，点击标记可查看/编辑该景点。是否符合预期？
10. 地图布局：【建议】行程编排页内嵌地图随操作联动，另设一个"路线总览"大地图页（可切换显示某一天或全部）。接受吗？
11. 景点图片：第一版要不要给景点存图片？【建议：不存，控制范围】
12. 酒店的数据形态：【建议】酒店=一类特殊地点（类型=酒店，带"每晚价格"字段），每天的"当晚住宿"从已录入的酒店地点中选择。对吗？
13. 跨城日的市内衔接（如 Day3 北京→上海，酒店→北京南站这段）：也纳入管理吗？【建议：第一版跨城日只管理大段（高铁/飞机），市内衔接可由用户手动添加普通交通段，不强制】

## C. 活动与时间排程

14. 活动时刻的产生方式：【建议】用户只定当天首个活动的开始时间，后续时间轴自动推算（游玩时长+交通耗时串联）；任一活动也可锁定时刻或手动改。接受吗？
15. 活动时长：每个活动必须有"预计时长（分钟）"，默认取景点的建议游玩时长、可改。对吗？
16. 景点开放时间的参与深度（三选一）：
    - a) 第一版仅作文本备注展示
    - b) 结构化：每日统一时段（如 08:30–17:00）+每周闭馆日（如周一），供冲突检测用【建议】
    - c) 完整分星期/季节/节假日规则（复杂，不建议）
17. 冲突检测第一版做哪些：时间重叠 / 排到闭馆时段 / 交通衔接不上（上一切结束+交通耗时 > 下一活动开始）/ 当天结束过晚（如超过 23:00）？【建议：全做，前三项优先】
18. 冲突的处理：仅提示（列表/时间轴标红）不阻断保存，对吗？
19. 活动标签的作用域：用户全局自定义（跨计划复用）还是单计划内？【建议：全局】
20. 餐饮活动：吃饭就是挂在餐厅地点上的普通活动，系统不做特殊支持（如自动插午餐时段）？【建议：是】
21. 每天的"日备注"字段（如"今天要早起赶高铁"）需要吗？PDF 每日页可展示。【建议：要】

## D. 交通

22. 备选方案交互：【建议】对一段路程点"计算交通"，系统并列给出步行/骑行/驾车/公交等 2–4 个方案（距离、耗时、参考费用），用户选定一个才生效进入行程与预算。接受吗？
23. 交通费用来源：打车/驾车费用地图 API 可估价；公交票价不一定准；高铁飞机无免费价格 API。【建议：有参考价就自动带出，以用户可改的手填为准】
24. 交通方式清单确认：步行、骑行、驾车（自驾）、打车、公交、地铁、火车（市际）、飞机、轮渡——有增减吗？
25. 推荐规则（D21）：【建议】按距离阈值推荐默认方案（<800m 步行；<3km 骑行/公交；>3km 驾车/打车；>50km 提示考虑火车），用户可改。可接受吗？
26. 跨城大段（高铁/飞机）：手填班次与时刻（如 G101 09:00–13:30），作为特殊交通段参与时间轴推算。对吗？
27. 交通段展示信息：方式、距离、耗时、费用、班次号（跨城）——还有要补充的吗？

## E. 路线优化

28. 单日优化目标确认为"当天总交通耗时最短"，同时尽量避开闭馆时段。对吗？
29. 单日景点数上限预期 ≤12 个，够吗（此规模精确算法可保证全局最优且秒出）？
30. 锚点支持：能否把某活动"固定时刻"（如预约 10:00 的项目），其余活动围绕锚点优化顺序与时间？【建议：支持，预约类场景天然需要】
31. 优化结果的应用：【建议】点"优化当天路线"→预览新旧对比（地图+时间轴）→确认后应用。接受吗？

## F. 预算与实际花费

32. 预算构成确认：活动费（门票等）+ 交通费 + 住宿费（酒店每晚价格×晚数）；餐饮不设单独类（用户自建活动）；是否需要"其他"杂项类？
33. 汇总口径：日预算=当天活动+交通（住宿费单独列不计入某天？）；总账=全部。金额自动汇总，可否允许"机动预算"一项兜底手填？【建议：是】
34. 超支提醒形式：编辑页实时红字提示 + PDF 预算页标注即可，不需要站内通知/消息中心。对吗？
35. 实际花费模块形态：
    - a) 对着计划逐项记录实际金额（与预算项 1:1）
    - b) 自由流水账（任意记一笔：金额+说明+归属天）
    【建议：a 为主 + 允许追加"计划外支出"】
36. 对比分析输出：每项差额、每日差额、总计差额、执行率（已花/预算）——表格即可还是也要简单图表（条形/环形）？
37. 住宿的实际花费：按晚录入还是一笔总额？

## G. PDF 导出

38. 每日安排表的列：时间段、活动/景点名称、地点、交通（方式+耗时）、费用、备注——竖版 A4 下建议精简，要哪些？
39. 路线示意：【建议】每天一张静态地图（当日点位+序号+连线），由后端调用高德静态地图 API 生成（适合服务端出图）。接受吗？对清晰度有特别要求吗？
40. 封面图来源：用户上传 / 预设精美模板图 / 不放图。【建议：预设模板+可选上传】
41. 打包清单页：【建议】预置常见分类模板（证件/衣物/电子/药品/其他）+用户可增删改，PDF 中渲染为勾选框清单。接受吗？
42. 页眉页脚：页眉=计划标题；页脚=页码+生成日期。还要别的吗（如署名"XX 的旅行计划"）？
43. 导出流程：编辑页按钮→后端生成（数秒）→浏览器直接下载；不做 PDF 历史版本管理。对吗？

## H. 技术与部署

44. Vben Admin 用法确认：整体骨架（登录、计划列表、系统设置）用 Vben；"计划编辑器"（地图+时间轴+拖拽）作为其内的自定义页面深度开发。另外确认使用 Vben v5（Vue3 + Vite + TypeScript）？接受吗？
45. 服务器与数据库：已有现成的服务器/MySQL，还是全新环境（由我提供 docker-compose：Nginx + Node 后端 + MySQL 一键部署）？
46. 地图 API key：由部署方（你）在高德/百度开放平台注册，配置到系统设置中全局使用。个人开发者认证后免费额度对本系统足够。可以吗？
47. 图片存储（封面图等）：【建议】第一版存服务器本地磁盘固定目录，不引入对象存储。接受吗？
